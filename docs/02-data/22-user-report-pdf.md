# Generating a PDF Report for a User

## Problem

Administrators needed a printable/exportable representation of a user's identity, status and system accesses. The existing UI was useful for interactive management but was not a convenient artifact for sharing or archiving.

## Context

The report is generated by the backend. The frontend requests the PDF as binary data and triggers a browser download.

## Investigation

The main design decision was to keep PDF generation out of the controller. The controller/application flow should assemble the required information, while a dedicated PDF abstraction handles document generation.

## Root Cause

The reporting requirement crossed several concerns: user retrieval, access retrieval, DTO mapping, document generation and browser download. Keeping those responsibilities separated prevents the report feature from turning into a large controller action.

## Solution

The application builds a report DTO containing:

- user ID;
- name;
- username;
- e-mail;
- job role;
- application profile;
- active status;
- creation date;
- creator information;
- system access records.

A PDF generator then converts this report model into a byte array.

## Technical Flow

```text
GET/POST report request
        ↓
Application use case
        ↓
Load users
        ↓
Load accesses
        ↓
Build report DTO
        ↓
PDF generator
        ↓
byte[]
        ↓
HTTP response
        ↓
Browser download
```

## Why This Solution

The application layer remains independent from the concrete PDF implementation. This makes the use case easier to test and allows the document-generation mechanism to evolve independently.

## Frontend Download

The SAPUI5 controller receives the binary response, creates an object URL and uses a temporary anchor element to trigger the download.

The browser therefore handles the final file transfer without exposing document-generation details to the UI.

## Result

A single user can be exported as a self-contained PDF containing both identity information and access information.

## Lessons Learned

Binary endpoints require a different frontend handling strategy from normal JSON APIs. The request abstraction needs to support blob responses explicitly.

## Possible Improvements

Possible future additions include report templates, configurable sections, generated timestamps, localization and automated PDF tests.
